# Protected settings and notification ordering

## Contract

A keychain failure or a credential-recovery conflict must not freeze unrelated preferences. The settings owner keeps protected legacy bytes in their original localStorage slot or native file. It writes only redacted provider configuration to a separate preferences record. Failed credential edits remain session drafts.

The local overlay uses `bettershape-settings-redacted-v1` while the primary record needs protection. The native canonical preferences record uses `settings-preferences.json`. Native preferences remain authoritative after migration. A compatibility-file cleanup failure does not turn a committed preferences write into a failed write or block native reconciliation. The old `settings.json` remains a compatibility source and receives a redacted replacement only when the credential guard permits it. Removing the native preferences record during promotion would introduce a second-file ordering race, so promotion does not remove it.

Startup reads legacy credentials before applying redacted preferences. `mergeRedactedPreferences` preserves the supplied base's credential and routing bundle. It does not use the global-settings secret merge as a substitute for the supplied base. It strips incoming provider credentials even when a redacted record has been tampered with. Desktop writes wait until hydration has reconciled edits made during startup.

## Dependency findings

The previous native path used `@tauri-apps/plugin-store`, but the capability file grants none of its commands. Adding a general store permission would grant a path-taking API rather than the two files this feature needs.

The native plugin also does not report every failed file read through `load`. In store version 2.4.2, `StoreBuilder::build_inner` discards the result of `store_inner.load()`. A corrupt primary can therefore appear to be an empty successful store. Treating that result as replacement authority would destroy the original bytes.

The replacement uses two fixed-file native commands. It does not add a plugin capability, CSP source, filesystem scope or dependency. The registered store plugin remains unchanged for compatibility; the settings renderer no longer calls it.

Primary sources checked:

- The installed store package's `dist-js/index.js` and `index.d.ts` for `load`, `get`, `set`, `delete` and `save`.
- [Store 2.4.2 command permissions](https://github.com/tauri-apps/plugins-workspace/blob/store-v2.4.2/plugins/store/permissions/autogenerated/commands/load.toml). The load command has no preconfigured path scope.
- [Store 2.4.2 native builder and file implementation](https://github.com/tauri-apps/plugins-workspace/blob/store-v2.4.2/plugins/store/src/store.rs). Loading discards parse/read errors, and saving writes directly to the destination file.
- [Store 2.4.2 command dispatch](https://github.com/tauri-apps/plugins-workspace/blob/store-v2.4.2/plugins/store/src/lib.rs). The caller supplies a path.
- Existing `ai_vault` SHA-256 revision use, native command registration, application URL configuration, and the shared `provider-default-headers.json` for local contract checks.

## Native ownership

`commands/settings.rs` owns the process-wide I/O mutex and the fixed-file command boundary. The caller must be a named application window at the packaged app origin or the configured development origin in a debug build. Packaged origin checks reject alternate ports. This permission check is independent of the close-consent policy.

`core/settings_file.rs` owns the file operations. It rejects unknown filenames, symlink targets, invalid JSON, invalid record shapes, oversized data, nonempty provider keys and private provider-header values. Both credential storage and settings validation use the same public-header helper and compiled JSON defaults.

The command returns an opaque SHA-256 revision. A writer supplies that revision, not a second plaintext copy of the old credential record. The native mutex covers comparison and replacement. A stale revision fails without replacing the current record. The core also compares the original parsed value and refuses to remove unowned record keys or unknown top-level settings fields.

Writes serialize into a bounded buffer and stage only the new redacted record. The temporary file uses exclusive creation, and Unix permissions are `0600`. The writer flushes the file before replacement and removes its temporary file on an ordinary write or rename failure. It does not create a plaintext legacy backup. Process crashes can leave a redacted temporary file. The implementation does not claim directory-fsync durability through power loss.

## Notifications

Storage events and Tauri events are invalidation hints, not settings snapshots. A receiver reads the current durable record and never republishes the event payload. Native code emits the hint after a preferences write commits, so a closing sender does not own notification delivery.

When localStorage is unavailable, the renderer waits for its queued native writes before reading canonical native preferences. Request generations, the queued-write identity and the live settings identity reject late read completions. Failed persistence does not authorize replacing unsaved memory state. Notifications cannot supply provider credentials.

This prevents the reported delayed-event rollback. Per-renderer serialization and native compare-and-replace are not a claim that independent simultaneous whole-snapshot edits are field-wise mergeable. Contention can reject a write. Original records remain intact, and a later user edit retries through a fresh read.

They cover protected local/native preferences, unreadable native primary storage, recovery conflicts, credential/routing preservation, delayed Tauri and storage events, and tampered notification credentials. The source restoration ran under `finally`.

The native filesystem helper and shared header helper compile and execute in an isolated Rust 1.88 crate. Eight tests cover corrupt-primary preservation, secret rejection, public headers, stale comparisons, filename validation, unowned data, size limits, symlinks on Unix and application-window labels. Isolated Clippy runs with `--no-deps -- -D warnings`.

The isolated crate uses the actual repository helpers and upstream sources at the versions in `Cargo.lock`. Its temporary dependency manifests select only the standard-library JSON feature graph and omit unused optional and development dependencies. Upstream source is unchanged. Dependency warnings about omitted optional feature declarations are not application warnings. Full native Cargo remains blocked by uncached dependencies in the restricted environment.

The stale-endpoint fixture now makes the new canonical preferences record stale too. ## Fields this build does not model

The preferences file is replaced wholesale on every save, so a field written by a
newer build (or by a downgrade) is only safe if the writer resolves the record it
read against the snapshot it is about to commit. `queueDesktopPersistence` now
passes the read record through `mergeSettingsOverlay(DEFAULT_SETTINGS, read,
snapshot)`: the snapshot's values win, every key of the record the snapshot does
not set is kept, and unknown entries inside maps such as `ai.providers` survive
with them. Redaction is not weakened by the merge - the snapshot was already
redacted, the native validator still refuses a record that carries a credential,
and the overwrite copy of the record carries whole values for maps, so an unknown
key is never interleaved into a value this build did write.

The canonical file is deliberately *not* merged this way. It is the one file where
an unmigrated plaintext credential can still live, and re-emitting the record
verbatim on every save would keep writing that credential back. Unknown top-level
keys are instead refused by `settings_file::write` ("Settings record contains
unowned fields") rather than silently dropped, and the renderer's ownership check
(`canReplaceStoredSettings`) keeps a file holding an unmigrated credential on the
preferences path until the keychain has it.

`settings_file::write`'s unowned-field check is now documented as deliberately one
level deep, with the reason attached: deleting an entry *inside* a branch this
build models - a provider connection, a header, a shortcut - is a first-class
action whose value no longer carries that entry, so a path-level check would
refuse every such write. A regression covers that deletion
(`allows_deleting_an_entry_inside_a_modelled_branch`), and the harness control
still fails exactly the swap test whose protection it reverts.

## Recovery after a rejected canonical read

A rejected read of the canonical preferences file used to be swallowed. The
queue then opened a fresh adapter for the same path, so the retry acquired
overwrite authority for a record this renderer had never read, and a failed
initialization stayed cached. Four consumer regressions reproduce that with the
pre-change renderer (the exact pre-change source is `de8205f:lib/settings/store.ts`, which a
control run restores under `finally`): overwriting unread preferences after recovery, no explicit
retry, losing edits made during a failing retry read, and reusing a second read's
revision for the first write.

The renderer now keeps a pending hydration context (`before`,
`localPreferences`, `localRecord`, `primaryApplied`, optional `preferences`)
until the canonical record has actually been read and merged:

- Reads and writes are serialized, and the write reuses the hydration read's
  adapter and revision. A rejected canonical read aborts the write instead of
  obtaining fresh authority.
- `initSettings()` retries an incomplete initialization while coalescing any
  initialization already in flight.
- A readable legacy primary still hydrates while canonical preferences are
  unavailable; that automatic hydration rebases the comparison baseline so it is
  not mistaken for a user edit when preferences recover.
- Preferences written before the primary was readable are projected through
  `projectSettingsOverlay(defaults, live, ...known)`: fields whose primary value
  is still unknown are omitted rather than serialized as defaults, and the same
  sparse projection is used for the local record so a restart cannot expand those
  defaults back into authority.
- A key recovered after the vault receipt was issued revokes that receipt, so a
  stale acknowledgement cannot erase a credential first read later.

Verification: 98 renderer tests across `settings-bridge-ordering`,
`settings-desktop-store`, `settings-hydration`, `settings-persistence` and
`ai-vault-fallback` pass, `tsc --noEmit` and `eslint --max-warnings=0` are clean,
and the eight new regressions fail with the pre-change renderer restored under
`finally`. Sparse structural fields merge field-by-field; arrays and open-ended
maps stay whole values, so deletions recorded in the overlay survive
(`mergeSettingsOverlay`, covered by a dedicated test).

Limitations that remain: an explicit edit to a value that happens to equal the
displayed default is still only detected by value, because no touched-field mask
is tracked. Whole-snapshot compare-and-replace is not a field-wise multi-window
merge. The settings file's Windows-only open path
(`FILE_FLAG_OPEN_REPARSE_POINT` in `core/settings_file.rs`, which rejects a link
swapped in between the pre-open check and the open) now type-checks and lints
clean for `x86_64-pc-windows-msvc` and `aarch64-pc-windows-msvc`, and a change to
that line fails those two targets while the Linux and macOS targets stay clean -
but no Windows or macOS binary was executed, so the replacement behavior itself
remains unverified. See `native-toolchain-and-cross-target-verification.md`.
