BetterShape runs on your machine and calls model providers directly with the keys you add. There is no account, no proxy, and no server that decides whether a request is allowed.

## Where keys live

Keys go into the operating system's credential store:

| Platform | Store |
| --- | --- |
| macOS | Keychain |
| Windows | Credential Manager |
| Linux | Secret Service (gnome-keyring, KWallet) |

Provider API keys, search and Composio keys, and connection-header values are persisted only in the OS credential store. New settings writes and cross-window settings events redact these values, even when the keychain is unavailable.

If a save fails, the edit remains an unsaved draft in that window. Settings > Providers shows a warning and a **Retry saving** action. Unlock or enable the OS keychain, then retry before closing. App-controlled window closes warn about unsaved credentials. A crash, forced termination or reload can lose a draft; the app does not create a plaintext recovery file. An unfinished write recorded in local metadata blocks automatic credential recovery after restart. Use **Review saved keys** to approve the displayed destinations, or re-enter the affected key. The review never displays key values and does not apply if settings change while the dialog is open.

Older installations may already have plaintext credentials in localStorage or `settings.json`. BetterShape leaves each existing settings copy untouched until migration succeeds. Settings changes may remain unsaved during that migration. If the copies disagree, BetterShape preserves both and asks you to review the saved keys or re-enter the affected keys or header values rather than choosing silently.

Credential updates use a process-wide native coordinator and observed revisions, not a per-window success cache. A clear retains a non-secret generation marker in the keychain so an older in-flight write cannot restore the removed value, including after restart. Conflicting updates pause synchronization in that window and require reloading settings or explicitly editing the credential again; a newer key is not copied into an older endpoint configuration. New vault records bind each credential to its destination in the same OS-vault record. Provider bindings include the base URL, wire format and authentication style. Search bindings identify the search provider, and Composio bindings identify the account. A stale settings write cannot silently move that saved key to a different destination. Legacy raw keychain values remain readable but need destination review unless a matching legacy settings copy establishes the pairing. Older builds do not understand versioned records and may require keys to be re-entered after a downgrade.

Keys are never sent anywhere except the provider endpoint you configured (OpenAI, Anthropic, Google, or your own OpenAI-compatible base URL).

## What leaves the machine

| Feature | Traffic |
| --- | --- |
| Chat, tools, captions, images, speech | One HTTPS request per call to the provider you configured. |
| Semantic code index | Embedding requests to the provider whose key you enabled, or nothing when that is off. |
| Web search tool | The search provider you configured (Tavily or Brave), or nothing when it is off. |
| Plugins tool | Composio, with your own Composio key. |
| Everything else | Local files, a local index, local history. |

Every request carries `bettershape/<version>` as its user agent plus the headers its provider's preset asks for (open the **Request headers & auth** section on a provider card to see them). Model ids are routed by their `provider/` prefix, so a request only ever goes to a provider you configured.

## Rules of thumb

| Kind | Meaning |
| --- | --- |
| **Local only** | Provider keys, chat history, and indexes stay on this machine. |
| **Provider authoritative** | Your provider decides rate limits and billing, not us. |
| **No gate** | Nothing in the app requires a sign-in. Chat needs a configured provider key, and says so when one is missing. |
